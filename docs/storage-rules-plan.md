# Storage Rules Plan

This document tracks Firebase Storage security rules for admin-managed image uploads.

## Scope

- Add `storage.rules` as a draft rules file.
- Document how image paths should be organized.
- Keep `firebase.json` commented out.
- Do not deploy rules.
- Product photo upload UI exists in the admin product editor.
- Do not modify existing image assets or protected content files.

## Current Rule Model

The draft Storage rules use the same `adminUsers/{uid}` allowlist as the admin shell and Firestore rules.

Approved admins can upload images to public image folders:

- `product-images/{fileName}`
- `event-images/{fileName}`
- `site-content-images/{fileName}`
- `other-images/{fileName}`

Objects in those folders are publicly readable so product, event, and site content images can render on the public site after a future backend-read phase. Public listing is denied.
The `other-images` folder is a holding area for reviewed admin media that is not yet linked to products, events, or site content.

Admin-private files can be stored at:

```text
admin-private/{firebaseAuthUid}/{fileName}
```

Only the matching approved admin can read or write those private image files. Public listing is denied.

## Upload Limits

The admin UI treats 10 MB as the website-performance threshold. Images over 10 MB should be optimized for the website by default so the storefront stays fast.

The draft rules allow image uploads only when:

- the user is an approved active admin
- the file is under 25 MB
- the uploaded content type matches `image/*`

The 25 MB draft hard cap leaves room for a rare admin override when Jette intentionally wants to keep a higher-resolution original. That override should be deliberate, not the default upload path.

Everything else is denied by default.
Original admin uploads between 10 MB and 25 MB require these updated Storage rules to be reviewed and deployed before they will work against Firebase.

Public image folders allow object reads but deny listing so visitors can load known image URLs without browsing the bucket.

## Important Guardrails

- These rules must be reviewed before deployment.
- `firebase.json` is not activated in this phase.
- Existing local image files remain the public storefront source of truth until a later approved backend-read/image migration phase.
- Public image path names should be stable before Jette starts uploading files.
- Storage rules depend on Firestore admin records, so Firestore rules and first-admin bootstrap must be handled first.

## Open Questions

- Should the 25 MB admin override cap be tightened before rules are deployed?
- Should image file names be generated by the app instead of typed by admins?
- Should deletes be allowed, or should old images be archived?
- Should there be separate folders for drafts versus published images?
